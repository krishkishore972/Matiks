# Matiks — web recreation

A **web-only** recreation of the Matiks mental-math and puzzle arena, reverse
engineered from the shipped Android build `com.matiks.app` 1.51.0 (XAPK). It is a
working app, not a click-through: every board is generated by a real engine, every
attempt is timed and scored, and 1v1 duels are played live against another browser
through a real server.

There is no mobile app in this repository. The deliverable is the Next.js app in
`apps/web`, the HTTP API in `apps/api`, the live WebSocket game server in
`apps/ws`, and the shared rules and domain in `packages/core` and
`packages/server`.

## Quick start

```bash
pnpm install
pnpm db:up                   # Postgres 17 in Docker, host port 55432
pnpm --filter api dev        # HTTP API   http://localhost:4000
pnpm --filter @repo/ws dev   # live games ws://localhost:4001
pnpm --filter web dev        # http://localhost:3000
```

The web app reads `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_WS_URL` at build time.
Start it with both servers attached:

```bash
cd apps/web && \
  NEXT_PUBLIC_API_URL=http://localhost:4000 \
  NEXT_PUBLIC_WS_URL=ws://localhost:4001 \
  pnpm dev
```

…or leave the variables unset and the app runs entirely offline against
`localStorage`, which is useful for working on the UI without Docker.

Port 55432 is deliberate: `docker-compose.yml` does not take 5432, so it will not
collide with a Postgres you already run. `apps/api/.env.example` and
`apps/ws/.env.example` list every setting; the defaults match the compose file,
so no `.env` is required.

Other useful commands (all from the repository root):

| Command | What it does |
| --- | --- |
| `pnpm dev` | Web + API + WebSocket together via Turborepo |
| `pnpm dev:api` / `pnpm dev:ws` | One server only |
| `pnpm db:up` / `pnpm db:down` | Start / stop Postgres |
| `pnpm db:generate` | Generate a Drizzle migration from the schema |
| `pnpm db:migrate` | Apply pending migrations |
| `pnpm db:reset` | Drop and rebuild the development database |
| `pnpm --filter web build` | Production build (type-checks as part of the build) |
| `pnpm test` | Web engine tests + server domain/duel tests + WS wire tests |
| `pnpm check-types` | TypeScript across every package |
| `pnpm lint` | ESLint with `--max-warnings 0` |
| `pnpm --filter @repo/ws smoke` | End-to-end duel against running servers |

Requires Node 24+ (see `engines` in `package.json`) and pnpm 11.

## What is implemented

**Navigation and shell** — a centred 520px app column with a sticky top bar
(pies + streak) and a five-tab bottom nav (Arena, Puzzles, Compete, Quests,
More), matching the reference app's navigation model. See
[docs/reference/ui-inventory.md](docs/reference/ui-inventory.md).

**Daily Challenge** (`/daily`) — Sudoku, KenKen, Cross Math, Math Maze and
Hectoc, seeded from today's date so every player gets the same five boards.
Division bands and the minimum-score rule are both surfaced.

**Snacc / Infinite Puzzle ladder** (`/puzzles`) — Queens, Tango, Zip, Pipes and
Wend, endlessly generated, with each puzzle's own rule set enforced and
Snacc Skips purchasable. (Snacc is the endless ladder in the reference app, not
the shop — the shop is the Pi Store.)

**Duels** (`/compete`, `/play/[gameId]`) — Sprint, Fastest Finger, DMAS, Mind
Snap, Flash Anzan, Pin Ball Recall and Ability Duels (Sum of Squares), all
60-second formats except Flash Anzan's three rounds and Pin Ball's eight boards.
Each duel ends with a blitz shape derived from the lead across three 20-second
windows.

**Live 1v1** (`/play/sprint`, `/play/fastestfinger`, `/play/dmas`) — "Find a live
opponent" queues a real matchmaking ticket on the WebSocket game server. Two
browsers in the queue are paired into the same game, the server serves the
questions one at a time and checks each answer against its own key, and both
seats see the score move in real time over the game's event stream. If nobody is
waiting by the documented `botEligibleAtMs` deadline, the AlphaBot takes the seat
and is labelled as such.
See [docs/reference/server-protocol.md](docs/reference/server-protocol.md).

**Scoring, ratings and progression** — puzzle score from difficulty, accuracy and
speed; Elo-style per-mode ratings; XP, levels, an XP booster; quests and rewards;
streaks with purchasable shields; the Pies economy and the Pi Store. With the API
attached these are server-authoritative and shared across devices.

**Profile and statistics** (`/profile`, `/more`) — lifetime stats, accuracy,
median time, per-mode ratings and recent plays.

**Leaderboards** (`/leaderboard`) — global/friends/college scopes across the five
evidenced categories. Rankings are real plays from the `plays` table; seeded
AlphaBot rows are flagged `bot`.

**States** — loading, empty, success and error states on every route, including
the "below minimum score" path that explains why a play did not count.

## Architecture

```
apps/web
├── lib/games/            pure seeded engines — no React, no DOM, no Math.random
├── lib/services/         Backend seam: LocalBackend (storage) + HttpBackend (API)
├── lib/state/player.tsx  React context over that seam
├── lib/hooks/            session stopwatch + accuracy ledger
├── components/games/     one component per board
├── components/GameHost   shared game chrome: how-to-play, timer, result sheet
├── components/LiveDuel   server-refereed 1v1 over the WebSocket
└── app/                  routes

apps/api
├── src/app.ts            Express 5: JSON, CORS, auth header, error handler
├── src/routes.ts         validated routes: player, plays, leaderboard, store, quests
├── src/validation.ts     Zod schemas for every request
├── src/index.ts          boot: migrate, seed bots, listen
└── drizzle.config.ts     drizzle-kit → packages/server/drizzle

apps/ws
├── src/messages.ts       Zod schemas for the wire vocabulary
├── src/hub.ts            WebSocket: search, play, replay, clock
├── src/index.ts          raw ws listener, waits for the API's schema
└── scripts/duel-smoke    end-to-end multiplayer check

packages/server           domain + persistence, shared by both processes
├── src/db/schema.ts      Drizzle schema: the single source of the DB shape
├── src/db/client.ts      pg pool + Drizzle client
├── src/db/migrate.ts     Drizzle migrator
├── src/db/repo.ts        profile, plays, store, quests, leaderboards
├── src/domain/questions  seeded question bank + the answer key
├── src/domain/stream     append-only game event stream, replay and resync
├── src/domain/duel       create/start/answer/settle, AlphaBot driver
├── src/domain/matchmaking tickets, rating window, bot fallback
└── drizzle/              generated SQL migrations

packages/core             shared by client and server, so rules cannot drift
├── src/rng.ts            mulberry32 + FNV-1a (deterministic boards)
├── src/scoring.ts        minimum scores, scoring, bands, Elo, XP
├── src/quests.ts         quest definitions and counters
├── src/catalog.ts        the 17 modes and their metadata
├── src/economy.ts        day keys, level curve, store items
├── src/leaderboard.ts    board taxonomy and which games feed each
└── src/protocol.ts       the wire types both sides import
```

The server stack is deliberately small: **Express 5** for HTTP, raw **`ws`** for
the game channel, **Zod** at both entry points, and **Drizzle ORM** over Postgres.
The schema lives in `packages/server/src/db/schema.ts`; `pnpm db:generate`
produces the SQL and `pnpm db:migrate` applies it, so the database shape and the
typed queries cannot drift. The HTTP API and the WS process share no in-process
state — only the database and `packages/server`.

Three decisions shape everything:

1. **Determinism.** All board generation goes through `rng.ts` (mulberry32 +
   FNV-1a string hash). `Math.random()` is never used for boards, so a daily
   puzzle is identical for everyone on a given date, a replay rebuilds the same
   question bank, and tests are repeatable.
2. **One copy of the rules.** XP, Elo, scoring, quests, the level curve and the
   day key live in `packages/core` and are imported by both the browser and the
   server. A rule cannot drift between the two because there is only one.
3. **A backend seam.** `Backend` (`apps/web/lib/services/backend.ts`) has two
   implementations — `LocalBackend` over `localStorage` and `HttpBackend` over
   the API — selected by `NEXT_PUBLIC_API_URL`. No component knows which one is
   in use.

Tests:

- `pnpm --filter web test` — engines (uniqueness, solvability, validation,
  rejection of illegal moves), reflex generators, Mind Snap tap scoring, Pin
  Ball's 1/0.5 rule, scoring/band/shape tables.
- `pnpm --filter @repo/server test` — question-bank determinism and answer
  correctness, the cursor guard (no score farming), monotonic stream replay and
  resync, duel settlement with Elo changes, draw handling, the minimum-score
  rule, and matchmaking (human pairing + AlphaBot fallback). The database tests
  skip themselves when Postgres is not reachable, so the suite still runs
  offline.
- `pnpm --filter @repo/ws test` — the Zod wire schema: every documented message
  type, plus rejection of unknown modes, malformed JSON and invalid answers.

## Honesty about data

Nothing simulated is presented as real:

- **Bots are labelled.** The AlphaBot is the recovered fallback, appears as
  "AlphaBot" in the duel, and its leaderboard rows carry a `bot` badge.
- **Memory duels say what they are.** Mind Snap, Flash Anzan and Pin Ball Recall
  generate boards on-device, so their live mode only compares reported scores.
  They are practice-only in the UI rather than pretending otherwise.
- **No friend graph.** The `friends` leaderboard returns your row plus other real
  accounts — it never dresses a bot up as a friend.
- **Contests** (80 in 8, Survival Saturday, Speed Run, Road to Kolkata) are the
  interface the app exposes, marked **Needs server**, with an offline practice
  link instead of a fake bracket.

## Not included

Authentication, ranked seasons, contests and bracket play, the Feed/Nets social
surfaces, the Patches and Flip Match ladder entries (their rules are not
recoverable from the artifact), and paid currency. Nothing above is faked in its
place.
